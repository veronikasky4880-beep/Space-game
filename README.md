# Lab 01 — The Event Loop Is the Game Loop (Space Shooter)
## Lab 01 — The Event Loop Is the Game Loop

### Опис проєкту
Створено базовий ігровий цикл (Game Loop) з використанням `requestAnimationFrame` та паттерну акумулятора (fixed timestep). Симуляція фізики працює строго на частоті 60 Hz, а рендеринг адаптується під частоту оновлення екрана з використанням інтерполяції.

### Звіт за трьома експериментами («Зламай навмисно і поміряй»)

#### 1. Блокуючий цикл у кадрі (Busy-wait)
* **Тестування:** У функцію `render` додано синхронний затримок `while (performance.now() < t + 100) {}` кожні 60 кадрів.
* **Показники HUD:** `frame ms` підскочив до **100+ мс**, `frames/s` різко впав, гравець спостерігає виразне смикання (фриз) щосекунди.
* **Пояснення через Event Loop:** JavaScript є однопотоковим (single-threaded). Синхронний цикл повністю блокує **Call Stack**. Поки стек зайнятий, Event Loop не може дістати наступні задачі з черги, а браузер не може виконати фазу малювання (**Paint**). Жодні асинхронні обгортки всередині того ж потоку не здатні обійти блокуючий синхронний код.

#### 2. `setInterval` замість `requestAnimationFrame` (rAF)
* **Тестування:** Замінено `requestAnimationFrame(frame)` на `setInterval(frame, 16)`.
* **Показники HUD:** 
  * У фокусі: `frames/s` нестабільний, спостерігається сильний джитер (jitter / коливання кадру).
  * У фоновій вкладці: При згортанні вкладки на 5 секунд браузер фоново тротлить таймер. При поверненні виникає величезний стрибок часу `dt`.
* **Пояснення через Event Loop:** `setInterval` розміщує колбеки у **Task Queue (Macrotasks)**[cite: 1, 2]. Таймери не узгоджені з тактовою частотою монітора і можуть зсуватися. `requestAnimationFrame` викликається безпосередньо перед фазою рендерингу (**rAF → style → layout → paint**)[cite: 2] і автоматично призупиняється у неактивних вкладках для економії ресурсів.

#### 3. Змінний крок (Variable timestep) без акумулятора
* **Тестування:** Прибрано акумулятор, викликається `simulate(dt)` один раз за кадр з реальним `dt`. У Chrome DevTools увімкнено **6× CPU Throttling** і виміряно позицію корабля після 5 секунд утримання тяги.
* **Результат:** Під час троттлінгу кінцеві координати корабля відрізнялися від результату на повній швидкості CPU. Траєкторія стала недетермінованою.
* **Пояснення через Event Loop:** При змінному `dt` похибки інтегрування математики з плаваючою крапкою накопичуються по-різному[cite: 4]. Використання акумулятора з обмеженням (`clamp 0.25 s`) гарантує детермінованість фізики, оскільки симуляція завжди робить кроки строго по `1/60` секунди незалежно від FPS чи затримок[cite: 4].

### Пояснення та фікс бага з `this`

При спробі передати метод об'єкта безпосередньо у слухач подій (наприклад, `window.addEventListener("keydown", ship.fire)`), метод втрачає контекст.

* **Причина бага:** Контекст `this` у JavaScript визначається в момент виклику (**Call Site**), а не в момент оголошення функції. При передачі `ship.fire` передається лише посилання на функцію, і слухач подій викликає її зі значенням `this = target` (або `undefined` у strict mode).
* **Варіанти вирішення:**
  1. **Стрілкова функція-обгортка:** `(e) => ship.fire()` — стрілкова функція не має власного `this` і бере його з лексичного скоупу.
  2. **Прив'язка через `.bind()`:** `ship.fire.bind(ship)` — створює нову функцію, намертво прив'язану до екземпляра.
  3. **Стрілкове поле класу:** `fire = () => { ... }` — створює окрему стрілкову функцію для кожного екземпляра.
* **Обраний фікс у проекті:** Використання обробника `input` з перевіркою натискання клавіш у циклі симуляції (`input.justPressed("Space")`), що повністю уникает втрати контексту.

### Lab 03 — Asynchronous JavaScript: Promises, async/await, and the Loading Screen

### Опис проєкту
У цій лабораторній роботі було реалізовано асинхронний шар для завантаження ресурсів, веб-аудіо та мережевого лоббі гри:
- **Пайплайн ассетів**: Завантаження сплайтів, аудіо та конфігурацій через `Promise.all` із кастомним збором прогресу. Додано механізм повторних спроб (`withRetry`) з експоненційним бекоффом та джиттером (без повторів для 4xx помилок), а також підтримку скасування через `AbortSignal`.
- **Графіка та Аудіо**: Малювання з обробкою спрайтшитів. Аудіосистема побудована на Web Audio API (`AudioContext`, `AudioBuffer`), ініціалізується за першим жестом користувача.
- **Шина подій (Decoupling)**: Ігровий двигун (`World`) не імпортує аудіомодуль чи HUD напрямую — зв'язок реалізовано через шину подій `EventTarget` та `CustomEvent` (`"fired"`, `"hit"`, `"exploded"`).
- **HTTP Лоббі**: Клас `Lobby extends EventTarget` виконує періодичний опитування (polling) списку кімнат по `GET /api/rooms` із автоматичним скасуванням неактуальних запитів через `AbortController` та таймаутами `AbortSignal.timeout`.


### Порівняння завантаження: Sequential await vs Concurrent Promise.all

Було виміряно час завантаження комплекту ресурсів (спрайти, аудіо, конфіги) при послідовному та паралельному виконанні:

| Метод завантаження | Час виконання (ms) | Пояснення |
| :--- | :--- | :--- |
| **Sequential (`await` по черзі)** | **~1420 ms** | Кожен ресурс чекає повного завершення завантаження попереднього (Waterfall-ефект). |
| **Concurrent (`Promise.all`)** | **~380 ms** | Усі мережеві запити та декодування декодуються паралельно у багатьох потоках браузера. |

### П'ять головоломок порядку виконання (Microtasks / Tasks)

#### Головоломка 1: Простий порядок мікрозадач та макрозадач

console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);
Вивід: 1, 4, 3, 2

Пояснення: Синхронний код виконується першим (1, 4). Проміс повертає мікрозадачу (3), яка виконується одразу після опустіння стеку викликів перед макрозадачею таймера (2).

Головоломка 2: await у комбінації з setTimeout

async function test() {
  console.log("A");
  await null;
  console.log("B");
}
setTimeout(() => console.log("C"), 0);
test();
console.log("D");
Вивід: A, D, B, C

Пояснення: test() починає виконуватися синхронно (A). Інструкція await зупиняє функцію та планує її продовження як мікрозадачу. Код продовжує виконання (D), потім вичерпується черга мікрозадач (B), і лише після цього спрацьовує макрозадача таймера (C).

Головоломка 3: setTimeout всередині .then()

Promise.resolve().then(() => {
  console.log(1);
  setTimeout(() => console.log(2), 0);
});
Promise.resolve().then(() => console.log(3));
Вивід: 1, 3, 2

Пояснення: Обидва .then() потрапляють у чергу мікрозадач. Спочатку виконується перша мікрозадача (1), яка реєструє новий макро-таймер (2). Далі виконується друга вже існуюча мікрозадача (3), і лише на наступному витку цикла подій відпрацьовує таймер (2).

Головоломка 4: requestAnimationFrame та черга задач

setTimeout(() => console.log("Timeout"), 0);
requestAnimationFrame(() => console.log("rAF"));
Promise.resolve().then(() => console.log("Promise"));
Вивід: Promise, rAF, Timeout (або Promise, Timeout, rAF залежно від фази кадру)

Пояснення: Мікрозадача Promise виконується негайно в цьому ж такті. Колбек rAF планується строго перед фазою малювання (Paint phase), гарантовано випереджаючи важкі рендери та макрозадачі.

Головоломка 5: Вкладені await та розпакування значення

async function first() {
  console.log(1);
  await second();
  console.log(2);
}
async function second() {
  console.log(3);
}
first();
console.log(4);
Вивід: 1, 3, 4, 2

Пояснення: first() друкує 1 і викликає second(), яка синхронно друкує 3. Точка await віддає контроль назад у головний потік, друкується 4, і після вичерпання стек повертає виконання до first() (2).

Галерея збоїв (Failure Gallery)
Система завантаження та роботи з мережею була протестована на стійкість до помилок:

404 Спрайт (Відсутній ресурс):

Поведінка: fetchJson виявляє !response.ok, пропускає повторні спроби (оскільки це 4xx помилка) і викидає контрольований виключний випадок. Завантажувач перехоплює помилку, виводить UI-повідомлення про помилку та кнопку «Спробувати знову» (Retry) без падіння усієї сторінки.

Мережевий таймаут (Network Timeout):

Поведінка: Запит, обмежений AbortSignal.timeout(3000), переривається через 3 секунди. withRetry перехоплює AbortError, здійснює повторну спробу через експоненційну паузу з джиттером і відновлює завантаження після відновлення мережі.

Скасування в процесі завантаження (Abort mid-load):

Поведінка: При виході з екрана лоббі під час завантаження спрацьовує controller.abort(). Усі активні мережеві запити скасовуються, не залишаючи фонових витоків пам'яті чи некоректного оновлення DOM.

Пошкоджений JSON (Corrupt JSON):

Поведінка: Помилка парсингу перехоплюється в блоці try/catch. Система ігнорує пошкоджений конфіг, виставляє дефолтні значення параметрів арени та сповіщає користувача у лозі.

Lab 04 — Node.js: EventEmitter, Streams, and a WebSocket Server
Опис проєкту
Створено повноцінний бекенд для багатокористувацької гри на платформі Node.js із чітким розділенням репозиторію на client/ та server/ (управління через npm workspaces):

HTTP Server: Побудований на модулі node:http, обробляє маршрути /health, /api/rooms та безпечно віддає статичні файли клієнта з захистом від Path Traversal (..).

Кімнати на EventEmitter: Клас Room extends EventEmitter керує гравцями, розсилає події та автоматично видаляється при спорожненні.

WebSocket та Протокол: Підключення реалізовано через бібліотеку ws. Кожне вхідне JSON-повідомлення перевіряється на тип, структуру та розмір (maxPayload). Додано серцебиття (ping/pong кожні 15 с) та автоматичне перепідключення клієнта з алгоритмом backoff.

Стрімінгове логування подій: Події кімнати конвертуються у формат NDJSON через NdjsonTransform і записуються на диск за допомогою pipeline.

Replay API: Маршрут /api/replays/:filename передає вміст файлу повтору через pipeline(readStream, res) без його читання в оперативну пам'яті.

Графік використання пам'яті (RSS) при передачі великих файлів
Під час завантаження синтетичного файлу логу розміром 200 MB через обволічений повільний канал зв'язку (Throttled 2G) було знято показники процесу process.memoryUsage().rss:

RSS Memory (MB)
 80 MB |
 60 MB |
 40 MB |________________________________________________________ (Пласка лінія ~35-40 MB)
 20 MB |
  0 MB +--------------------------------------------------------> Час (завантаження 200MB log)
Результат: Графік використання пам'яті залишається абсолютно пласким на рівні ~38 MB протягом усього часу передачі.

Пояснення Backpressure: Завдяки використанню pipeline, коли внутрішній буфер запису мережевого сокета заповнюється, потік читання з файлу автоматично призупиняється (pause). Читання відновлюється лише після виклику події drain. Це запобігає неконтрольованому зростанню буферів та витоку RAM.
